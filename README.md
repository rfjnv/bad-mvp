# БАД Маркет — MVP интернет-магазина витаминов и БАД (Узбекистан)

Next.js 15 (App Router, TypeScript strict) + Tailwind CSS + Prisma (SQLite) + Zod.

## Запуск с нуля (3 команды)

```bash
npm install
npm run db:setup
npm run dev
```

Откройте http://localhost:3000 — витрина, и http://localhost:3000/admin — админка.

**Админ по умолчанию** (создаётся сид-скриптом):
- логин: `admin`
- пароль: `admin12345`

Смените пароль в проде — сид-скрипт предназначен только для демо-данных.

## Команды

| Команда | Что делает |
|---|---|
| `npm run dev` | Запуск дев-сервера |
| `npm run build` | Продакшен-сборка |
| `npm run db:setup` | Алиас: миграции + сид (см. package.json) |
| `npx prisma migrate dev` | Применить миграции |
| `npm run seed` | Засеять базу тестовыми данными (24+ товара, 9 заказов, админ) |
| `npx prisma studio` | Визуальный просмотр базы |

Если `npm run db:setup` не определён в вашей копии — выполните вручную:
```bash
npx prisma migrate dev
npm run seed
```

## Стек и структура

- `prisma/schema.prisma` — модель данных (Product, Category, Order, OrderItem,
  Banner, Bundle, BundleItem, SubscriptionRequest, TelegramSubscriber,
  AdminUser, Counter)
- `prisma/seed.ts` — сид: категории, товары, тестовые заказы, админ
- `src/lib/i18n.ts` — все строки интерфейса одним объектом (для будущей локализации на узбекский)
- `src/lib/payments/` — модуль оплаты, см. ниже
- `src/app/api/**` — API-роуты с валидацией Zod
- `src/app/admin/**` — защищённая middleware админка
- `src/middleware.ts` — авторизация `/admin/*` и `/api/admin/*`

## Оплата: песочница vs боевой режим

Онлайн-оплата в Узбекистане (Payme, Click) требует юрлица и подписанного договора
с провайдером. На этапе MVP боевых ключей нет, поэтому:

- Интеграция реализована структурно: `src/lib/payments/types.ts` описывает интерфейс
  `PaymentProvider` (`createPayment`, `verifyCallback`, `handleWebhook`), а
  `src/lib/payments/payme.ts` и `src/lib/payments/click.ts` — две реализации.
- Если переменные окружения с ключами провайдера не заданы, провайдер работает
  в **режиме песочницы**: покупатель попадает на `/payment/sandbox/[orderId]`,
  через 2 секунды платёж автоматически помечается `PAID`, и заказ проходит по
  всему циклу — от оформления до страницы успеха.
- Роуты вебхуков реальны и рабочие: `/api/payments/payme/callback`,
  `/api/payments/click/callback`. Для Payme подпись проверяется через Basic Auth
  (`Paycom:secretKey`), для Click — через `sign_string` (md5 по полям запроса
  и секретному ключу), как в боевом протоколе провайдера.

### Чтобы включить боевой режим

Заполните в `.env`:

```
PAYME_MERCHANT_ID="..."
PAYME_SECRET_KEY="..."

CLICK_MERCHANT_ID="..."
CLICK_SERVICE_ID="..."
CLICK_SECRET_KEY="..."
```

Как только переменные заданы, `getPaymentProvider()` перестаёт использовать
песочницу и строит боевые ссылки/проверки подписи. Код менять не нужно — это
конфигурация.

**Важно сказать вслух на демонстрации**: подключение реальных ключей — это
организационный вопрос (юрлицо + договор с Payme/Click), а не технический.
Код к этому готов.

## Готовые наборы (Bundles)

`Bundle`/`BundleItem` — курируемые комплекты товаров со скидкой (`/bundles`,
`/bundles/[slug]`, управление в `/admin/bundles`).

- Скидка набора активна только пока в корзине лежит **ровно по 1 шт.** каждого
  товара из набора — так `OrderItem.priceAtPurchase` остаётся одной ценой на
  всю строку, без дробления по юнитам внутри одной позиции.
- Кнопка «Добавить набор в корзину» выставляет количество каждого товара
  набора в 1 и сохраняет применённый набор в `localStorage` браузера.
- Скидка **пересчитывается на сервере** в `/api/orders`: клиент присылает
  только `appliedBundleSlug`, а сумму и разрешённость скидки сервер проверяет
  сам по актуальным данным набора в БД — процент скидки с клиента не
  принимается никогда.
- Наборы в сиде подобраны так, чтобы не попадать в категории-предостережения
  модуля совместимости (`src/lib/compatibility.ts`).

## Напоминания в Telegram

Как и оплата, реализовано структурно с песочницей при отсутствии боевого бота:

- `src/lib/telegram.ts` — `sendTelegramMessage()`; без `TELEGRAM_BOT_TOKEN`
  работает в режиме песочницы (реального запроса нет, возвращается превью
  сообщения — как в `src/lib/payments/*`).
- Подключение — на странице `/tracker`: генерируется `deviceId` в
  `localStorage`, создаётся `TelegramSubscriber`, показывается диплинк на
  бота (`https://t.me/<username>?start=<deviceId>`).
- `/api/telegram/webhook` — реальный вебхук: Telegram присылает `/start
  <deviceId>`, роут привязывает `chatId` к подписчику. Без настроенного бота
  этот роут просто никто не вызывает.
- Список товаров из трекера синхронизируется на сервер (`routineSnapshot`)
  при каждом изменении — без этого напоминание не знало бы, что писать.
- `/admin/telegram` — список подписчиков + кнопка «Отправить напоминания
  сейчас»; без боевого токена показывает, что было бы отправлено, вместо
  реальной отправки.

### Чтобы включить боевой Telegram-бот

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите токен.
2. Заполните в `.env`:
   ```
   TELEGRAM_BOT_TOKEN="..."
   TELEGRAM_BOT_USERNAME="your_bot_username"
   ```
3. Разверните проект на публичном HTTPS-домене и зарегистрируйте вебхук:
   ```
   https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://ваш-домен/api/telegram/webhook
   ```
4. Чтобы напоминания уходили сами по себе каждый день, повесьте вызов
   `POST /api/admin/telegram/send-reminders` на внешний cron (Vercel Cron,
   GitHub Actions schedule и т.п.) — сам по себе Next.js по расписанию ничего
   не запускает.

## Временный деплой на Render

В репозитории есть `render.yaml` (Render Blueprint) — Render сам поднимет
сервис по кнопке «New → Blueprint», указав на этот репозиторий.

**Важное ограничение бесплатного тарифа**: SQLite-файл живёт в файловой
системе контейнера. На бесплатном плане Render контейнер «засыпает» после
15 минут бездействия и при следующем запросе поднимается заново из
образа — а значит база откатывается к тому состоянию, что было на момент
сборки (то есть к сиду). Для короткой демонстрации это не проблема (и даже
удобно — всегда чистое состояние), но заказы/изменения, сделанные во время
показа, не переживут «сон» сервиса. Для реальной персистентности нужен
платный план с постоянным диском либо переезд на внешнюю БД (Postgres).

## Ограничение окружения сборки (важно для разработчиков)

Prisma закреплена на версии **6.19.2**, а не на последней 7.x. Причина: в
песочнице, где собирался проект, недоступен хост `binaries.prisma.sh`,
откуда Prisma 7 качает нативные бинарники движка при установке — сеть
разрешала только `registry.npmjs.org`. Версия 6.19.2 подошла, потому что
её движок уже был закэширован в npm-реестре по факту установки в соседнем
проекте на этой машине. Функционально это никак не ограничивает MVP.

Если у вас есть доступ к `binaries.prisma.sh` (обычное окружение
разработки), можно обновиться:
```bash
npm i --save-dev prisma@latest
npm i @prisma/client@latest
npx prisma generate
```

## Изображения товаров

В сиде используются сгенерированные SVG-плейсхолдеры по категориям
(`public/products/*.svg`) — в песочнице сборки нет доступа к интернету,
поэтому реальные фото брендов взять было неоткуда. Замените `imageUrl` в
базе (через админку — загрузка изображения работает и сохраняет файлы в
`public/uploads/`) на настоящие фотографии перед продакшеном.

## Проверено перед сдачей

- Оформление заказа целиком, включая оплату в песочнице (Payme/Click) и
  наличные — стоки товаров уменьшаются в транзакции при создании заказа
- Админка: смена статуса заказа, включение/выключение товара, загрузка
  изображения, создание категории
- Мобильная вёрстка на 380px: бургер-меню, каталог в одну колонку, слайдеры
  и таблицы не ломаются
- Поиск без результатов — показывает пустое состояние с кнопкой сброса
  фильтров, а не пустой экран
- Несуществующий slug товара — отдаёт 404
